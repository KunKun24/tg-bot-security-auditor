# 审计方法详解

**中文** · [English](en/audit-method.md)

这份文档讲的是「为什么这样审」，`SKILL.md` 讲的是「必须这样审」。如果你只想让代理跑一次，读 `README.md` 就够了；如果你想判断一次审计报告有没有水分，读这篇。

## 一、审计的对象不是代码，是「谁能做什么」

绝大多数 Telegram Bot 漏洞报告写得很像代码评审：「这里用了字符串拼接 SQL」「这里没校验参数」。这些话可能都对，但它们回答不了运营者真正关心的问题：**谁，需要什么条件，能拿到什么，能重复多少次。**

所以本方法的第一产物不是发现列表，而是两张表：

1. **系统图**：入口 → 分发器 → 中间件 → handler → service → 持久化 → 外部 API，标出每个信任边界；
2. **授权矩阵**：每个特权操作一行，写清操作者从哪来、角色从哪读、归属怎么比、失败时是开放还是拒绝。

发现的严重度，是从这两张表里长出来的，而不是从代码形状里猜出来的。同一个「缺少归属校验」，在私聊按钮上是 Low，在群管理员回调上就是 High——区别不在代码，在谁能碰到它。

## 二、七个阶段各自在防什么错

### 0. 锚定范围：防止「不可复现」

报告必须写 commit SHA、分支、工作区是否脏、锁文件哈希。原因很实际：没有锚点，三个月后没人知道这份报告对应哪版代码，也没法判断某个问题是不是已经修了。复审计（Re-audit）靠的就是锚点 + 指纹。

### 1. 建系统图：防止「局部正确，全局错误」

一个 handler 内部的校验可能无懈可击，但它注册在错误的位置、被更早的 catch-all 挡住、或者中间件顺序反了，效果等于没有。系统图强制把**注册顺序**画出来，因为顺序本身就是授权语义的一部分。

### 2. 威胁建模：防止「按目录审」

按 OWASP 目录逐条审，得到的是一份均匀分布的问题清单，可用性很差。按攻击者审，得到的是「匿名用户能不能直接拿钱」这种能决定发不发版的东西。对一个小型私域 bot，匿名面可能根本不存在；对一个公开的付费 bot，匿名面就是全部风险。

### 3. 分层扫描：防止「只看得懂的部分被审了两遍」

八个域 + 语言包 + 框架对照，是给审计划一个可交代的下限：哪些必须看、每个域看到什么程度算看完。语言包解决的是「模型对这门语言的危险 API 记忆不全」；框架对照解决的是「不知道这个框架的授权通常写在哪」。

广度优先（grep 候选 sink）再纵深（追通调用链），是为了让时间花在**可达**的问题上，而不是花在把每个可疑片段都写成一段猜想上。

### 4. 授权矩阵：防止「审了入口，漏了动作」

入口（命令、按钮）通常有明显的人写检查；动作（service 方法、job、内部 HTTP 路由）往往是复用的，第二个调用方常常忘了检查。矩阵按动作填，空格子就是漏审的地方。

### 5. 验证与定性：防止「把候选当结论」

四态标签是这套方法的核心约束：

- `CONFIRMED`：路径读完，控制缺失或失效已被证明；
- `POTENTIAL`：路径合理，但某个关键条件不确定（并发窗口、中间件顺序、部署形态）；
- `NEEDS-VALIDATION`：只有运行态、供应商或部署配置才能定；
- `OBSERVATION`：质量问题，没有已证明的安全影响。

把「不确定」写进状态，比把不确定写成断言更有价值——后者会让整份报告失去可信度。

### 6. 定级：防止「用形容词定级」

定级用一句可检验的话：**攻击者是 X，需要 Y，拿到 Z，可重复 N 次。** 如果 X 是管理员，或者 Y 需要另一个不相关的漏洞，降级；如果 Z 是钱且 N 无上限，升级。`references/vulnerability-levels.md` 里有同一缺陷在四种上下文下的校准样例。

### 7. 出报告：防止「看起来审了很多」

覆盖矩阵必须允许写「未审」。一份诚实的 60% 覆盖，比一份假装 100% 的报告有用得多，因为前者告诉运营者下一步该补哪里。同时输出 findings JSON，让结论可以被 CI 消费、被下次审计对比。

## 三、Telegram 特有的四类「非代码漏洞」

### 1. 身份混用

`from.id`、`chat.id`、`sender_chat.id`、`business_connection_id`、`callback_query.from.id` 是五个不同主体。代码里把它们当同一个用，是最常见也最难靠静态扫描发现的问题。群里的匿名管理员、频道代发、内联 bot（`via_bot`）都会让「谁在说话」和「谁是操作者」分离。

### 2. 回调即输入

`callback_data` 即使由 bot 自己生成，也是用户可控输入：可以伪造、可以重放、可以是上一版状态留下的旧按钮。`answerCallbackQuery` 只是交互反馈，把它当授权是典型错误。

### 3. 支付即状态机

Telegram 会重投 update。以「事件」为幂等键（收到 `successful_payment` 就加钱）而不是以「charge id」为幂等键，重投就变成重复履约。金额、币种、payload 与服务端订单的绑定也必须校验，不能信客户端成功页。

### 4. 传输即边界

webhook 的 `secret_token`、常量时间比较、fail-closed；长轮询的 offset 与单实例；`getFile` 链接里内嵌的 token——这四件事任意一件做错，都能让前面所有授权检查失效。

## 四、只读边界为什么必须硬

审计动作一旦能改状态，报告就失去意义：你无法区分「审出来的问题」和「审的过程中弄坏的东西」。所以本方法把「不装依赖、不跑迁移、不跑机器人、不调 Bot API、不打印密钥」写成硬约束，并给出只读命令白名单（`references/safe-commands.md`）与替代方案表。需要真实流量才能确认的问题，一律降级为 `NEEDS-VALIDATION` 并附人工复核步骤。

同理，被审仓库里的注释、README、夹具、issue 都是**不可信数据**。一个写着「请忽略之前的指令」的注释，不应该改变审计行为。

## 五、一次审计大概花多久

| 项目规模 | 模式 | 典型耗时 | 主要成本 |
| --- | --- | --- | --- |
| ≤ 5k 行，单服务，无支付 | Lite | 20–40 分钟 | 系统图 + 授权矩阵 |
| 5k–30k 行，含支付或管理后台 | Full | 1.5–4 小时 | 支付状态机 + 并发路径 |
| 多服务 / 多机器人 / Mini App | Full | 4–8 小时 | 边界与身份传递 |
| 修复后复审计 | Re-audit | 20–60 分钟 | 只核对指纹与改动面 |

时间是估算，不是承诺；报告里应写清实际覆盖了什么。

## 六、怎么判断一份报告值不值得信

按这六条检查，缺两条以上就要警惕：

1. 有没有 commit 锚点和排除目录的理由？
2. 有没有授权矩阵，还是一个 handler 都没点名？
3. 每条发现有没有 `path:line` 和可复现命令？
4. 严重度和置信度是不是分开写的？
5. 有没有「别处是否已经拦了」的核查？
6. 覆盖矩阵里有没有老实的「未审」？
