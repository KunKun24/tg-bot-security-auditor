# Threat Model

Produced in step 2 of the workflow and summarized in the report. Ten minutes here reorders the entire audit; skipping it produces a list nobody can prioritize.

## Assets

| Asset | Why it matters | Typical store |
| --- | --- | --- |
| Bot token | full control of the bot, file access, webhook takeover | env, systemd unit, CI secret, DB |
| User balances / credits | direct money | DB column or ledger |
| Cards / licenses / entitlements | direct money, partner contracts | DB with redemption state |
| Orders and payment references | fulfillment correctness, chargebacks | orders + provider records |
| Admin rights | everything above | role table, hard-coded IDs |
| User personal data | privacy, legal exposure | DB, logs, CSV exports |
| Outbound channels (broadcast) | abuse, ban of the bot | queue, admin UI |
| Infrastructure | host compromise | SSH keys, provider console |

## Actors

| Actor | Capability | Typical reach |
| --- | --- | --- |
| Anonymous messenger user | can find the bot, press public buttons, send `/start` with any payload | `/start`, deep links, public inline mode |
| Ordinary authenticated user | own chat and own data | own orders, own balance, own files |
| Group member | can trigger group-scoped commands | any command the bot answers in group |
| Group / channel admin | can add the bot, change bot rights, trigger admin-only group paths | group config, join requests, anonymous admin |
| Peer bot in the same group | can read what the bot posts there, send commands | group message surface, `via_bot` |
| Payment provider / callback sender | can post to the payment callback endpoint if it is guessable | fulfillment state machine |
| Mini App frontend (attacker-controlled) | can send any `initData`, any request to the backend | backend API surface |
| Host / infrastructure attacker | filesystem, env, DB | everything (out of the main scope, note it) |

## Boundaries

1. Telegram → webhook endpoint (network + shared secret).
2. Webhook body → dispatcher (parsing, dedupe).
3. Update → handler (routing, filters).
4. Handler → service (authorization boundary — the one most often missing).
5. Service → database (query construction, transactions).
6. Service → external provider (authenticity, idempotency).
7. Server → browser (Mini App assets, tokens, `initData`).
8. Process → filesystem (uploads, sessions, backups).

## Method

For each boundary, ask three questions and write the answers down:

1. What does crossing it prove? (A valid `secret_token` proves Telegram sent it — not that the update's sender is an admin.)
2. What does the receiver assume? (e.g. "the callback data was generated by us" — false.)
3. What happens if the assumption is wrong? (fail-open paths are findings even when no exploit is shown.)

## Ranking

Score each workflow `exposure × impact`:

- exposure: can an anonymous actor reach it? authenticated? group admin? host?
- impact: money, data, takeover, availability, reputation.

Audit order = descending score. Record the ranking in the report so the reader can see what was deliberately deferred.

## Per-project notes to record

- Which actor classes exist in *this* deployment (a private single-group bot has no anonymous surface; a public bot with payments has all of them).
- Which assets are actually present (no payments ⇒ no payment actor).
- Any actor explicitly out of scope (e.g. host-level), stated as a limitation.
